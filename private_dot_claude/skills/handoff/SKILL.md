# Handoff

現在の会話を要約し、新しいエージェントが作業を継続できる引き継ぎ文書を書く。

`/compact` とは目的が違う。あちらは同一セッションの継続、こちらは**別セッション・
別エージェントへの受け渡し**が対象で、成果物としてファイルに残る。

## 出力先

下記の2点をユーザに確認する
1. **OS の一時ディレクトリに保存する**（Linux/WSL なら `/tmp` 配下）。
2. **CLIを実行してるターミナルに表示する**。
作業中のワークスペースを引き継ぎ文書で汚さない。保存したパスをユーザーに伝える。

## 書くこと

文書の冒頭に、受け取る側への指示として次の1行を置く:

> 【見込み】と書かれた記述は検証されていない。自分で測ってから判断の土台にすること。

- 何をしようとしていたか（目的とスコープ）
- どこまで終わったか
- 次に何をすべきか
- 判明している制約・前提・落とし穴
- **推奨スキル** — 次のエージェントが Skill ツールで起動すべきスキル名を列挙する

## 実測と見込みを分ける

事実を述べる記述には、行ごとにどちらかのラベルを付ける。

- **【実測】** — この会話で実行・観測して確かめた。何で確かめたか（コマンド・出力・ファイル）を添える
- **【見込み】** — 「〜すれば効くはず」「〜が原因だろう」のように、確かめていない

書き手の記憶だけで書いたものは【見込み】にする。受け取る側は、両者が同じ重みで並んでいると読み分けられず、外れた見込みを土台に後続の判断を積む。

URL・ポート・パス・ID は記憶から書かない。正本（設定ファイル・規約の資料・コマンドの出力）を書く直前に引き、出典を添える。引けなかったものは【見込み】にする。

## 書かないこと

**他の成果物に既に記録されている内容を複製しない。**
仕様書・計画・ADR・Issue・コミット・diff は、**パスまたは URL で参照する**に留める。
複製すると二重管理になり、参照先が更新されたときに引き継ぎ文書が嘘になる。

## 機密の取り扱い

API キー・パスワード・トークン・個人情報は伏字にする。
`rules/agent-security.md` の機密情報チェックに従う。

## 引数がある場合

ユーザーが引数を渡してきたら、それは**次のセッションで何に集中するかの指定**として扱い、
文書の内容をそれに合わせて絞る。
