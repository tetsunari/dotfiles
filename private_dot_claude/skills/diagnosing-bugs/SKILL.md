# Diagnosing Bugs: 調査ループ

原因を推測する前に、**バグを検出できる1コマンド**を作る。これが本スキルの中核であり、
`rules/ai-operations.md` 第9原則（推測での根本原因提示の禁止）の実行手順にあたる。

飛ばしてよいフェーズは、飛ばす理由を明示できる場合のみ。

## 機密の取り扱い

本スキルはコマンド・出力・取得した成果物を提示させる。**提示前に必ず秘匿値を `<REDACTED>` に置換**する。
認証情報は環境変数に置いたままループを組み、値そのものを画面に出さない。
取得した HTTP ログ等は認証ヘッダを含むため、シグナルのある行だけを引用する。

秘匿を落とした結果として診断に足りないなら、その旨をユーザーに伝えて判断を仰ぐ。

## Phase 1: フィードバックループを作る

**ここが本体。** このバグで赤くなる信号さえ手に入れば、二分探索も仮説検証も計装も、
すべてその信号を消費するだけの機械作業になる。信号が無いままコードを睨んでも解決しない。

ここに不均衡なほど労力を割く。粘れ。

### 構築手段（おおむねこの順に検討）

1. **失敗するテスト** — バグに届く seam であれば unit / integration / e2e どれでもよい
2. **curl / HTTP スクリプト** — 起動中の開発サーバーに対して叩く
3. **CLI 実行** — フィクスチャ入力を食わせ、既知の正常出力と diff する
4. **ヘッドレスブラウザ** — Playwright / Puppeteer で UI を駆動し DOM・console・network を検証
5. **キャプチャの再生** — 実リクエスト・ペイロード・イベントログを保存し、該当経路だけに流し込む
6. **使い捨てハーネス** — 依存をモックした最小構成で、当該コード経路を関数1呼び出しで叩く
7. **property / fuzz ループ** — 「たまに出力が壊れる」系は乱択入力を1000回流して破綻を探す
8. **二分探索ハーネス** — 既知の2状態の間で発生したなら `git bisect run` に載る形に自動化する
9. **差分ループ** — 同一入力を新旧バージョン（または2設定）に通して出力を diff する
10. **HITL スクリプト** — 最終手段。人間のクリックが必要なら、手順をスクリプト化して人間を駆動し、
    結果を機械可読な形で回収する

### ループを締める

ループは成果物として扱い、手に入れたら**締め上げる**。

- 速くできないか（セットアップのキャッシュ、無関係な初期化の省略、テスト範囲の絞り込み）
- 信号を鋭くできないか（「落ちなかった」ではなく症状そのものを assert する）
- 決定的にできないか（時刻の固定、乱数シードの固定、ファイルシステムの隔離、ネットワークの遮断）

30秒かかる不安定なループは無いのとほぼ同じ。2秒で決定的なループは武器になる。

### 非決定的なバグ

目標は「きれいな再現」ではなく**再現率を上げること**。トリガを100回回す、並列化する、
負荷をかける、タイミング窓を狭める、sleep を注入する。50%再現なら調査できる。1%では無理。

### ループを作れない場合

その時点で止まり、明示的に伝える。試した手段を列挙し、ユーザーに次のいずれかを求める。

- 再現する環境へのアクセス
- 秘匿処理済みの成果物（HAR、ログ、コアダンプ、時刻付きの画面録画）
- 本番への一時的な計装の許可

**ループ無しで仮説に進んではならない。**

### Phase 1 の完了条件

以下すべてを満たす**単一のコマンド**（スクリプトパス・テスト実行・curl のいずれか）を、
**すでに1回以上実行して**その実行と出力（秘匿処理済み）を提示できる状態。

- **赤くなりうる** — 実際のバグ経路を通り、**ユーザーが訴えた症状そのもの**を assert している。
  「エラーなく完走する」では不十分で、このバグを捕まえられなければならない
- **決定的** — 何度実行しても同じ判定（非決定的バグの場合は、固定された高い再現率）
- **速い** — 分ではなく秒
- **無人で回せる** — 人間の介在は HITL スクリプト経由のみ

このコマンドが存在する前にコードを読んで仮説を組み立てようとしていたら、**そこで止まる。**
いきなり仮説へ飛ぶことこそ、本スキルが防ごうとしている失敗そのものである。

## Phase 2: 再現と最小化

ループを回し、赤くなるのを確認する。

- 出ている失敗が、**ユーザーの言った症状**か（近所の別の失敗ではないか）。違うバグを直しても意味がない
- 複数回の実行で再現するか（非決定的なら、調査に足る再現率か）
- 後続フェーズで検証できるよう、症状（エラーメッセージ・誤った出力・所要時間）を控えたか

### 最小化

赤くなったら、**赤いまま到達できる最小のシナリオ**まで削る。
入力・呼び出し元・設定・データ・手順を**1つずつ**削り、都度ループを回し直し、
外すと緑になるものだけを残す。

これで Phase 3 の仮説空間が縮み（疑うべき可動部が減る）、Phase 5 の回帰テストがそのまま手に入る。

**残った要素すべてが必須**（どれ1つ外しても緑になる）状態が完了条件。
再現と最小化の両方が済むまで先へ進まない。

## Phase 3: 仮説を立てる

検証に着手する前に、**3〜5個の順位付きの仮説**を出す。1つだけ立てると最初の思いつきに固着する。

各仮説は**反証可能**であること。すなわち予測を伴うこと。

> 形式: 「もし X が原因なら、Y をすればバグは消える／Z をすれば悪化する」

予測を書けないものは仮説ではなく感想なので、捨てるか研ぎ直す。

**検証前に順位付きリストをユーザーに提示する。** ドメイン知識で順位が一変することが多く
（「3番なら先週デプロイした」）、既に潰した仮説も分かる。安価な確認で効果が大きい。
ただしここでブロックはしない。ユーザーが不在なら自分の順位で進める。

## Phase 4: 計装する

各プローブは Phase 3 の**特定の予測に紐づける**。**一度に変える変数は1つ**。

1. 環境が許すならデバッガ / REPL。ブレークポイント1つはログ10行に勝る
2. 仮説を弁別する境界に絞ったログ
3. 「全部ログしてgrep」は禁止

**デバッグログには必ず一意の接頭辞を付ける**（例 `[DEBUG-a4f2]`）。
後始末が grep 一発になる。付けなかったログは消し忘れて残る。

**性能劣化の場合はログではない。** まずベースラインを測る（計時ハーネス、`performance.now()`、
プロファイラ、実行計画）。測ってから直す。

## Phase 5: 修正と回帰テスト

回帰テストは**修正より先に**書く。ただし**正しい seam がある場合に限る**。

正しい seam とは、**呼び出し箇所で起きたのと同じバグのパターン**を再現できる位置のこと。
浅すぎる seam しかない場合（複数呼び出し元が絡むバグを単一呼び出しのテストで書く、
連鎖が再現できない unit テスト）、そこに置いた回帰テストは誤った安心を与える。

**正しい seam が無いこと自体が発見である。** 記録すること。
コードベースの構造がバグの封じ込めを妨げているというシグナルなので、次の工程へ申し送る。

正しい seam があるなら:

1. 最小化した再現をその seam のテストにする
2. 失敗するのを確認する
3. 修正を当てる
4. 通るのを確認する
5. Phase 1 のループを**最小化前の元シナリオ**に対して回し直す

## Phase 6: 後始末

完了を宣言する前に、以下すべてを満たすこと（`rules/verification-loop.md` の完了条件）。

- 元の再現手順で再現しなくなった（Phase 1 のループを回して確認）
- 回帰テストが通る（または seam が無いことを記録した）
- `[DEBUG-...]` の計装をすべて撤去した（接頭辞を grep して確認）
- 使い捨ての試作物を削除した（残すなら明示的にそれと分かる場所へ）
- 当たった仮説をコミット / PR メッセージに記した（次に踏んだ人が学べるように）
