# audit-skills

カスタムスキルのSKILL.mdを読み込み、品質・効率・安全性を分析し、検出した問題を自動修正する。

## 実行形式

```
/audit-skills [対象] [+観点]
```

### 対象パラメータ

| 指定 | 意味 |
|------|------|
| 省略 / `@all` | 全スキル検索 |
| `@プロジェクト名` | 指定プロジェクト内のスキル |
| スキル名 | 個別スキル指定 |

### 観点パラメータ

| 指定 | 意味 |
|------|------|
| 省略 / `+core` | コア10観点 |
| `+security` | コア + セキュリティ拡張 |
| `+portability` | コア + 移植性拡張 |
| `+reliability` | コア + 信頼性拡張 |
| `+full` | 全観点統合 |
| `+dynamic` | 多エージェント協調検証（Find→Verify→Synthesize） |

---

## 実装ステップ

### Step 1: 対象スキル収集

以下3つのパス層を並列検索する：

1. `~/.claude/skills/*/SKILL.md`（グローバル）
2. `<カレント>/.claude/skills/*/SKILL.md`（カレント）
3. `<カレント>/*/.claude/skills/*/SKILL.md`（サブプロジェクト）

- audit-skills自身は除外する
- Glob未検出時はBashでフォールバック

### Step 2: メタデータと内容読み込み

- 対象スキルのSKILL.md全てを並列Read
- プロジェクトのCLAUDE.mdを読み込む
- Skill()呼び出し先スキルも読み込む
- frontmatter / 本文行数 / 他スキル呼び出し名を記録

### Step 3: チェック実行

#### コア10観点（C1〜C10）

**C1: 指示矛盾**
同一操作の異なる手順、「する/しない」両立、スキル間仕様不一致

**C2: 指示不備**
エラー対処・判断基準の曖昧さ、分岐欠落、引数バリデーション不足、ロールバック無し

- **失敗コードとNG行動の対**: 失敗の種類を列挙するだけで終わっていないか。
  各失敗に「その時にやってはいけないこと」を対で書く。
  特に timeout・stalled は「処理が届かなかった証明にはならない」ため、
  盲目的な再送は二重実行を生む（AI運用第2原則の具体化）。
- **識別子の出所**: ID・ハンドルをレスポンスからパースさせているか。
  一覧の並び順・ドキュメントの例示から推測させる記述は誤爆源。
  値が変わる操作（移動・再作成）の後に古い ID が無効化されるなら明記する。

**C3: 指示過剰**
500行超スキル、重複指示、冗長な例示、汎用性喪失（200行超の場合は references/ への分離を検討）

**C4: セキュリティ**
機密ファイル除外、破壊操作確認、dangerouslyDisableSandboxの明確性、mainブランチ警告

- **探索的実行の禁止対象**: 使い方を調べる目的で、副作用のあるコマンドを
  引数省略で叩かせていないか。`<tool> create` のようなミューテーション系は
  引数を省いてもデフォルト値で**実際に実行される**。ヘルプ発見を促す記述には
  「引数省略で探ってよいのは読み取り系コマンドのみ」を併記する。

**C5: 速度最適化**
並列可能ステップの逐次実行、&&チェーン分割、重複ロジック

**C6: スキル間整合性**（複数対象時のみ）
役割重複、自前再実装、実装統一、前提条件不一致、用語統一

**C7: allowed-tools整合性**
使用指示のツール未登録、登録済み未使用、Agent/Skill指定不整合

**C8: トリガリング精度**
短すぎるdescription、フレーズ不足、類似スキル競合、機能とのギャップ

- **発火しない条件の明記**: 起動条件だけでなく「これでは起動するな」を
  description に書いているか。強力なスキルほど「役に立ちそう」で誤発火する。
  肯定条件の列挙だけでは境界が引けない。
  例: 「ユーザーが明示的に X と言った時のみ使う。バックグラウンド処理や
  並列作業に便利そうという理由だけで使ってはならない」
  確実に自動起動を止めたい場合は、文面での抑止より
  **`disable-model-invocation: true`**（手動 `/name` 起動のみに限定）が公式手段。
  文面での抑止は、自動起動は残したいが誤発火を減らしたい場合に併用する
- **前提条件のガード**: 実行環境の前提があるなら、最初の一手で検証して
  外れたら停止する手順が本文にあるか（環境変数チェック等）。
  前提が外れた状態での実行は誤操作に直結する。

**C9: 保守性**
CLAUDE.md重複、ハードコード値、責務過大（100行超複数機能）、過小（15行以下低独立性）

**C10: 使用性**
直感性欠落、確認頻度不適切、結果報告不十分、成功/失敗フォーマット未定義

**C11: コンテキスト設計**

2種類の負荷を分けて評価する。

- **コンテキスト負荷** — 毎セッション常駐するトークン。description がここに当たる
- **認知負荷** — 読み手（モデル）が判断に費やす量

チェック項目:

- **description の肥大**: description はルーティング判断の場であり、常駐コストそのもの。
  手順や規範の本文が混入していないか確認し、本文は SKILL.md 側へ移す。

  ⚠️ **自前でバイト数を集計しない。** Claude Code は skill listing に予算を設けており、
  実測値は公式コマンドが出す。自作の集計は機序を取り違えたうえに計測ミスも起こす
  （実際に「上位数本が占有して新規が埋もれる」という存在しない問題を報告した）。

  公式の挙動（docs.claude.com / skills）:

  - `description` と `when_to_use` の合算は **1,536 文字で truncate**
  - listing 全体の予算は **モデルのコンテキストウィンドウの 1%**
  - 予算超過時に落ちるのは「バイト数が多い順」ではなく
    **呼び出し頻度が低い順**。比率の大小は選別に影響しない

  したがって確認手順は以下に従う:

  | 目的 | 手段 |
  |------|------|
  | listing の実コストと最大寄与元 | `/doctor` |
  | 使われていないスキルの特定 | `/skill-doctor` |
  | 予算を広げる | `skillListingBudgetFraction`（例 `0.02`）／ `SLASH_COMMAND_TOOL_CHAR_BUDGET` |
  | 1本あたりの上限を変える | `skillListingMaxDescChars` |
  | 低優先スキルを名前だけにする | `skillOverrides` に `"name-only"` |

  スキル側でやるべきなのは**主要ユースケースを先頭に置く**こと（cap は予算と無関係に効くため）
- **情報の階層**: ①本文中の手順 ②本文中のリファレンス ③別ファイルへの分離、の3層に配置されているか。
  参照頻度の低い長大な表が本文に居座っていないか
- **先頭語**: トリガー語は先頭に寄せる。同義語は枝を分けず1本に畳む
- **既存概念の再利用**: モデルが事前学習で知っている語（seam, tracer bullet, poka-yoke 等）を使い、
  独自用語の発明を避ける
- **no-op の刈り取り**: モデルが既定で行うことを指示していないか
  （「注意深く読む」「正確に答える」等は書いても情報量がゼロ）
- **重複とキャッシュ**: rules/ や CLAUDE.md に既にある内容の再掲がないか。
  高コストな調査結果のみキャッシュとして持つ
- **外部ツール仕様の焼き付け**: 外部CLI・APIのフラグ一覧やサブコマンド表を
  SKILL.md に転記していないか。転記した瞬間からバージョンドリフトで腐り、
  しかも腐ったことに気付けない。「インストール済みバイナリが仕様の正典」と
  宣言し、`<tool> --help` やサブコマンド単体実行で都度発見させる形に寄せる。
  SKILL.md に残すのは「発見の入口」と「ヘルプに書かれていない落とし穴」のみ。

#### セキュリティ拡張（+security）

- 責任追跡性: コミット署名・ログ出力の追跡可能性
- Sandbox詳細分析: dangerouslyDisableSandbox全箇所の対象コマンド・理由・代替案評価
- 外部通信リスク: 取り消し困難操作の確認フロー
- 権限昇格分析: allowed-tools組み合わせの想定外権限取得リスク

#### 移植性拡張（+portability）

- 環境依存明示: OS・シェル・ツールバージョン・systemd前提の記述
- パスハードコード: ユーザー固有・絶対パス直書きの有無
- プロジェクト分離: グローバルスキルへの固有ロジック混在チェック

#### 信頼性拡張（+reliability）

- 障害許容性: 外部ツール失敗・ネットワーク・ファイル不在への対処
- 回復性: 途中失敗・状態変更後失敗のリカバリ手順
- 成熟性: 空入力・大量ファイル・権限不足の対処

### Step 4: レポート出力

```
## スキル監査レポート

対象: N個 | 観点: +core（等）

### 個別スキル結果

#### [スキル名]（行数:NN, スコープ:グローバル/プロジェクト）
| 観点 | 重大度 | 指摘 |
|------|--------|------|
| C#: 内容 | 重大/改善/情報 | 具体指摘 |

### スキル間指摘（複数対象時のみ）
| 観点 | 対象 | 重大度 | 指摘 |
|------|------|--------|------|
| C6 | skill1/skill2 | 重大/改善 | 具体指摘 |

### サマリー
- 重大（自動修正済み）: N件
- 改善（自動修正済み）: N件
- 情報（参考）: N件
```

#### 重大度基準

| 重大度 | 基準 | 修正方針 |
|--------|------|----------|
| **重大** | 実行誤り・セキュリティリスク・データ損失・実行時エラー | 即時自動修正 |
| **改善** | 効率悪化・保守困難・UX低下 | 自動修正 |
| **情報** | 軽微な余地・スタイル統一 | 修正しない（報告のみ） |

---

### Step 5: 自動修正

重大・改善の指摘をEditツールで順次修正する。修正方針：

- **C1（指示矛盾）**: 矛盾箇所を削除し、より明確な記述に統一する
- **C2（指示不備）**: エラー対処・ロールバック手順を補足する
- **C3（指示過剰）**: 重複指示・冗長な例示を削除しコンパクトにまとめる
- **C4（セキュリティ）**: 破壊操作前の確認フロー・機密ファイル除外を追記する
- **C5（速度最適化）**: 逐次ステップを並列実行に書き換える
- **C7（allowed-tools整合性）**: frontmatterのallowed-toolsを実態に合わせて更新する
- **C8（トリガリング精度）**: descriptionにトリガーフレーズを補強する
- **C9（保守性）**: ハードコード値を変数化・責務過大スキルは分割提案を添える
- **C10（使用性）**: 成功/失敗の出力フォーマットを明記する

修正完了後、変更差分のサマリーを出力する。

### +dynamic モード（多エージェント協調検証）

`+dynamic` 指定時は Step 3〜4 を以下の3エージェント協調に置き換える。

#### Dynamic workflow 概要

静的チェック（C1〜C10）では見落としやすい「文脈依存の問題・スキル間の暗黙的な依存・実行時の挙動ズレ」を多角的に検証する。

#### エージェント構成

**Find エージェント（問題洗い出し）**

```
役割: 対象スキルを徹底的に読み込み、以下の観点で問題を列挙する
- C1〜C10の全観点
- 実際の使用シナリオを想定したときに破綻するケース
- 他スキルとの連携時に生じうる不整合
- 指示の抜け漏れ・エッジケース未考慮
出力: 問題リスト（観点・重大度・具体箇所・理由）
```

**Verify エージェント（再検証）**

```
役割: Find エージェントの指摘リストを受け取り、各指摘を独立して再評価する
- 指摘が正当か（誤検知でないか）を確認
- 重大度の妥当性を評価
- Find が見落とした問題を追加検出
出力: 検証済み問題リスト（確認済み/却下/追加 の3分類）
```

**Synthesize エージェント（レポート統合）**

```
役割: Verify の出力を統合し、最終レポートを生成する
- 確認済み問題を優先度順に整理
- 修正推奨事項を具体的に記述
- /goal コマンドで使用できる「改善ゴール文」を生成
出力: 構造化レポート + 改善ゴール文リスト
```

#### 実行手順

1. Find エージェント起動（Agent ツール、バックグラウンド可）
2. Find 完了後 → Verify エージェント起動（Find 出力を引数に渡す）
3. Verify 完了後 → Synthesize エージェント起動
4. Synthesize レポートを Step 4 フォーマットで出力
5. Step 5（自動修正）を適用
6. 改善余地が大きい場合は `/goal` コマンドの使用を提案

#### +dynamic 使用例

```
/audit-skills audit-skills +dynamic
/audit-skills @all +dynamic
```
