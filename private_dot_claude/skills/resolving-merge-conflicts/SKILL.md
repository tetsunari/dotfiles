# Resolving Merge Conflicts

## 手順

1. **現状を把握する。** マージ / リベースの進行状態、履歴、衝突しているファイルを確認する。
   解消を始める前に退避ブランチ（`git branch backup/<名前>-pre-resolve`）を作り、ロールバック可能な状態にする。
   作成はユーザーに一言確認してから行う。

2. **各衝突の一次情報を辿る。** それぞれの変更が**なぜ**入ったのか、元の意図は何かを理解する。
   コミットメッセージを読み、PR を確認し、元の issue / チケットまで遡る。
   ここを飛ばした解消は、動くように見えて意図を壊す。
   gh が使えない・PR が見つからない場合は `git log <base>..<side> -- <file>` でコミットメッセージから読む。
   それでも意図が特定できない hunk は推測で解消せず、手順3でユーザーに確認する。

3. **hunk ごとに解消する。** 両方の意図を可能な限り保存する。
   両立しない場合は、**このマージの目的**に合う側を採る。目的が一意に決まらない場合は推測せず
   AskUserQuestion で、どちらの変更が消えるかを具体的に示して確認する。捨てた側のトレードオフは記録する。
   **新しい振る舞いを発明しない。** 意図を復元できない hunk は解消を止めてユーザーに報告する。
   `--abort` は使わず、途中状態を保ったまま報告する。

4. **プロジェクトの自動チェックを走らせる。** 典型的には型チェック → テスト → フォーマット。
   チェック手順は CLAUDE.md や package.json 等から特定する。失敗したらマージ前の基点で同じチェックを走らせて比較し、
   マージ起因のものだけ直す。既存の失敗は触らずに報告する。

5. **マージ / リベースを完了する。** 解消したファイルをステージしてコミットする。
   `git status` で意図しないファイルがないことを確認し、解消したファイルだけ `git add <file>` でステージする（`git add -A` は使わない）。
   push 済みブランチのリベースは履歴を書き換えるため、続行前にユーザー確認を取る。
   リベース中なら、全コミットが載りきるまで継続する。

## 完了条件

`~/.claude/rules/verification-loop.md` に従う。型チェック・テストがクリーンであることを**実際に実行して**確認し、
解消時に捨てた側のトレードオフがあればユーザーに「ファイル:hunk / 採った側 / 捨てた側と影響」の表で報告する。
