# TDD: テスト駆動開発

red → green のループを回す。本スキルは、そのループが**価値のあるテスト**を生むための条件を定める。
各節は実装の前と最中に参照する。書き終えてから読んでも意味がない。

## 良いテストとは

公開インターフェース越しに**振る舞い**を検証するもの。実装詳細ではない。
内部コードが大きく変わっても成立し続ける。

良いテストは仕様として機能する。「有効なカートで購入を完了できる」は、
提供している機能を正確に記述し、内部機構に触れていないためリファクタを跨いで生き残る。

## Seam: テストを置く場所

**seam** とは、内部に手を入れずに振る舞いを観測できる公開境界のこと。
テストは seam にのみ置く。内部コンポーネントに対しては書かない。

**合意済みの seam でのみテストする。** テストを書き始める前に、対象とする seam を提示し、
**ユーザーの承認を得る**。未承認の seam にテストを置いてはならない。

全部はテストできない以上、seam を先に合意しておくことで、
労力が重要な経路と複雑なロジックに集中する。

seam は少ないほどよい。既存の seam を新設より優先し、新設するなら可能な限り高い位置に置く。

## アンチパターン

- **実装結合** — 内部の協力オブジェクトをモックする、private メソッドを叩く、
  検証を別経路（DB を直接見る等）で行う
- **トートロジー** — 期待値を実装と同じ計算で組み立てる assert。常に通るので何も守らない
- **水平スライス** — テストを全部書いてから実装する。
  実際の振る舞いではなく**想像した振る舞い**を検証するテストができあがる

## ループの規律

- **red が先** — 失敗するテストを書き、それを通す最小限の実装を当てる
- **1周1スライス** — 1つの seam、1つのテスト、1つの最小実装
- **リファクタはループの外** — red-green の最中ではなくレビュー段階で行う（`tidying` に委譲）

## 完了条件

`rules/verification-loop.md` に従い、以下を満たすまで完了としない。

- 追加したテストが**追加直後に赤かった**ことを確認済み（赤を見ずに緑になったテストは信用しない）
- 修正後に緑
- 既存のテストスイート全体が通る
- 型チェック・lint がクリーン
