# Codebase Design

**deep module** を設計する。小さなインターフェースの背後に多くの振る舞いを置き、
きれいな seam に配置し、そのインターフェース越しにテストできる状態にする。

狙いは、呼び出し側にとっての**レバレッジ**、保守側にとっての**局所性**、そして双方にとっての
テスト容易性。

## 用語

以下の語をそのまま使う。「コンポーネント」「サービス」「API」「境界」で言い換えない。
語彙を揃えること自体が目的である。

| 語 | 意味 |
|---|---|
| **モジュール** | インターフェースと実装を持つもの。**規模を問わない**（関数・クラス・パッケージ・層をまたぐスライス） |
| **インターフェース** | 正しく使うために呼び出し側が知らねばならないすべて。型シグネチャに加え、不変条件・順序の制約・エラーの様態・必要な設定・性能特性を含む |
| **実装** | モジュールの中身 |
| **アダプタ** | seam においてインターフェースを満たす具体物 |
| **深さ (Depth)** | インターフェースにおけるレバレッジ。呼び出し側（およびテスト）が、学ぶインターフェース1単位あたりに動かせる振る舞いの量 |
| **seam** | そこを編集せずに振る舞いを変えられる場所。モジュールのインターフェースが存在する**位置**（Michael Feathers） |
| **レバレッジ** | 深さが呼び出し側にもたらすもの。学習量あたりの能力 |
| **局所性** | 深さが保守側にもたらすもの。変更・バグ・知識・検証が1箇所に集まること |

## deep と shallow

- **deep module** = 小さいインターフェース + 厚い実装 ← 目指す形
- **shallow module** = 大きいインターフェース + 薄い実装 ← 避ける

## 原則

- **深さはインターフェースの性質であって、実装の性質ではない。** 行数が多いことは深さではない
- **削除テスト** — そのモジュールを消したと想像する。複雑さが消えるなら、それは素通し層だった
- **インターフェースがテスト面である。** テストを置けるのはそこだけ（`tdd` スキルの seam と同じもの）
- **アダプタが1つなら仮の seam、2つで初めて本物の seam**

## テスト容易性のための設計

1. 依存は受け取る。中で作らない
2. 結果を返す。副作用を起こさない
3. 表面積を小さく保つ

## 関係

- モジュールはインターフェースをちょうど1つ持つ
- 深さはモジュールの性質
- seam はモジュールのインターフェースが在る場所
- アダプタは seam に座り、インターフェースを満たす
- 深さは呼び出し側にレバレッジを、保守側に局所性を生む

## 関連

- 構造のみの安全な整理は `tidying`
- seam を決めてテストを置くのは `tdd`
- 過剰設計の抑制は `kaizen` および `rules/core-principles.md`（シンプル第一）
