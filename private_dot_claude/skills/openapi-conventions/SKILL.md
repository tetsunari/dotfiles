# OpenAPI Conventions Skill

OpenAPIスペック編集における規約強制と品質ゲートを提供するスキル。

## 大原則：既存エンドポイントのパターンに従う

**変更前に必ず既存エンドポイントを確認する:**

```bash
# 既存のエンドポイント構造を確認
grep -A 30 "^  /existing-endpoint:" openapi.yaml | head -40
```

新しいエンドポイントは、最も近い既存エンドポイントをテンプレートとして使用する。
**勝手な改善・拡張を加えない。**

## 必須レスポンス構成

すべてのエンドポイントに以下を含める（既存に存在するもののみ）：

| ステータスコード | 用途 | 条件 |
|----------------|------|------|
| `400` | バリデーションエラー | リクエストボディ・クエリパラメータがある場合 |
| `403` | 認証・認可エラー | 認証が必要なエンドポイント |
| `404` | リソース未発見 | IDでリソースを特定するエンドポイント |
| `500` | 内部サーバーエラー | 基本的に全エンドポイント |

**追加してはいけないもの（要求されない限り）:**
- `409 Conflict` — 明示的に要求された場合のみ
- `422 Unprocessable Entity` — 明示的に要求された場合のみ
- その他の4xx/5xx — 明示的に要求された場合のみ

## 編集スコープの厳守

```
# 正しい姿勢
「このエンドポイントに400レスポンスを追加して」
→ そのエンドポイントの400のみ追加する

# やってはいけないこと
→ 他のエンドポイントも「ついでに」修正しない
→ 要求されていないdescriptionを追加しない
→ 既存フィールドのdescriptionを改善しない
→ スキーマの命名を「より良い名前」に変えない
```

## スキーマ参照パターン

エラーレスポンスは必ず既存の共有スキーマを参照する：

```yaml
# 既存のパターンを確認して同じ$refを使う
responses:
  '400':
    description: Bad Request
    content:
      application/json:
        schema:
          $ref: '#/components/schemas/ErrorResponse'  # 既存の参照先に合わせる
```

## 新規エンドポイント追加手順

1. **既存エンドポイント確認**: 最も近い既存エンドポイントを `grep` で探す
2. **テンプレートとしてコピー**: 構造をそのままコピーし、差分のみ変更
3. **スコープ確認**: 要求された変更のみか確認
4. **必須レスポンス確認**: 400/403/404/500が適切に含まれているか確認

## ブランチ差分マージ手順

```bash
# 差分を可視化してから着手
diff branch-a/openapi.yaml branch-b/openapi.yaml

# コンフリクト箇所を特定
grep -n "<<<<<<\|>>>>>>>" openapi.yaml
```

マージ時は：
- どちらか一方を「正」として採用する（両方の良いとこどりで改変しない）
- 既存の命名・フォーマットを維持する
- マージ後に `cdk synth` や OpenAPI linter で検証する

## レビューチェックリスト

編集後に確認：
- [ ] 要求されたエンドポイント・フィールドのみ変更したか
- [ ] 既存エンドポイントのdescription・命名を変更していないか
- [ ] 要求されていないステータスコードを追加していないか
- [ ] エラーレスポンスの `$ref` が既存パターンと一致しているか
- [ ] UUIDパラメータの形式が既存と統一されているか
