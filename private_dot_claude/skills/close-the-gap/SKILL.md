# Close the Gap: 指示と現実のギャップを埋める

## Core Principle

AIの性能が上がるほど、成否を分けるのは人間側の指示品質。指示と現実の間には常にギャップがあり、それを埋める作業は実装の前・中・後それぞれで必要になる。

## 4つの未知フレームワーク

| 分類 | 内容 | 対処 |
|---|---|---|
| 既知の既知 | 明示された前提 | そのまま実装 |
| 既知の未知 | 分かっていないと自覚している領域 | 質問・調査で埋める |
| 未知の既知 | 当たり前すぎて言語化していない判断基準 | ブラインドスポット・パスで顕在化 |
| 未知の未知 | コードベースの落とし穴など気づいていない制約 | プロトタイプ・参照物確認で顕在化 |

## 実装前（Before）

### 1. ブラインドスポット・パス
実装対象の周辺で「言語化されていないが当然守るべき制約」を洗い出す。既存コードの類似実装・命名規則・エラーハンドリング方針・権限境界を確認し、要求文には書かれていない暗黙のルールをリスト化してユーザーに提示する。

### 2. プロトタイプで潜在ニーズ顕在化
UI/UXやAPI形状など「見れば分かる」性質のものは、文章で仕様を詰めるより先に簡易プロトタイプ（モック・スケッチ・サンプルレスポンス）を提示し、フィードバックを得る。

### 3. 優先度付きインタビューで曖昧さ解消
**委譲**: 決定木を辿る深いインタビューが必要な場合は `/grill-mi` を、フェーズ式の構造化インタビューには `/dig` を使う。本スキル内では重複実装しない。

### 4. 参照物による正確性担保
**委譲**: 一次情報（ソースコード・仕様書）による事実確認が必要な場合は `evidence-based` スキルに従う。本スキル内では重複実装しない。

### 5. 変更が入りやすい箇所の事前計画
要求の中で「後から変わりそうな部分」（外部仕様待ち・ステークホルダー未確定の箇所等）を特定し、その部分だけ設計を疎結合にする、または実装順序を後回しにする計画を立てる。

## 実装中（During）

### 6. 実装ノートで計画外判断を記録
計画時点で想定していなかった判断（エッジケース対応・命名の変更・想定外のライブラリ制約など）が発生した都度、その場で以下の形式を記録する。

```
## 実装ノート
- 判断: [何を決めたか]
- 理由: [計画時点でなぜ想定していなかったか／なぜその判断に至ったか]
- 影響範囲: [ファイル/機能]
```

## 実装後（After）

### 7. 検証資料で承認者を支援
実装完了時、レビュアー・承認者が変更の妥当性を素早く判断できるよう、変更内容・確認済み動作・未検証項目を簡潔にまとめる（`verification-loop.md` の完了基準と組み合わせて使う）。

### 8. クイズで理解度確認
実装内容についてユーザー自身の理解が追いついているかを、3〜5問程度の簡潔な確認質問（AskUserQuestion不要、テキストで可）として提示する。「なぜこの設計にしたか」「この変更が壊しうるものは何か」を問う。

## Integration

- **grill-mi** / **dig**: 手法3（優先度付きインタビュー）はここに委譲
- **evidence-based**: 手法4（参照物確認）はここに委譲
- **task-planner**: タスク分解が必要な大規模実装では先にこちらを使う
- **verify** / **verification-loop.md**: 手法7（検証資料）の実動作確認部分と連携
