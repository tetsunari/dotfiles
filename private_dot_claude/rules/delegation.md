# サブエージェント委譲基準

> コスパよく運用するサブエージェント活用戦略に基づく委譲判断ルール

## 委譲しない条件（オーバーヘッド損）

- 1〜2ファイルのみの編集
- 既に調査済みで実装箇所が自明なタスク
- 30秒以内に終わる軽微な修正

## コンテキスト保護のための委譲（最優先）

**ツール出力は一度親コンテキストに入ると、以降の全ターンで再送され続ける。**
使用量はターン数の二乗で増えるため、出力量の見積もりが委譲判断の第一基準になる。

以下は**必ず**サブエージェント（`code-explore` / `Explore` / `test-runner`）に逃がす。
結論だけ受け取り、生出力は親に持ち込まない：

- 出力が数百行以上になると予想される調査系コマンド（全文検索・ログ走査・大量ファイルの集計）
- 結果の大半を捨てる探索（「どこにあるか」を知りたいだけの grep/find）
- テスト・ビルドの実行と結果確認（失敗時のみ該当箇所を親に持ち帰る）

親で直接 Bash を実行する場合は、出力を先に絞ってから返す：

- `head` / `tail` / `wc -l` / `--format` / `-q` で必要な行だけにする
- 長時間コマンドは `run_in_background` で回し、完了後に要約だけ読む
- ファイル全文の Read は、対象箇所が特定済みのときだけ。探索目的なら Grep か委譲

## 委譲マトリクス

| 作業内容 | 委譲先 | 判断基準 |
|---------|--------|---------|
| 広範なコード調査・シンボル検索 | `code-explore` | 複数ファイル横断・依存関係追跡が必要 |
| 仕様明確な実装 | `implementer` | 実装箇所特定済み・設計判断不要 |
| 複雑な実装・大規模変更 | `heavy-implementer` | 3ファイル以上・設計判断あり |
| テスト実行・結果確認 | `test-runner` | テスト実行のみ |
| コードレビュー | `code-reviewer` | コード変更後・PR作成前 |
| エラー根本原因調査 | `error-investigator` | スタックトレース・ビルドエラー |
| セキュリティ審査 | `security-reviewer` | 認証・ユーザー入力・APIエンドポイント |
| ドキュメント更新 | `doc-updater` | README・codemap更新 |
| デッドコード除去 | `refactor-cleaner` | 未使用コード・重複整理 |
| 仕様・ベストプラクティス調査 | `spec-researcher` | 新ライブラリ導入・設定変更前 |
| Web検索 | `web-researcher` | 最新情報・外部ドキュメント参照 |

## 複数タスクの圧縮

独立した複数タスクは**1回の呼び出し**にまとめて委譲コストを削減する：
- ❌ 3回に分けて委譲
- ✅ 「A・B・Cをまとめて対応して」と1プロンプトで委譲

## モデル選定根拠

| モデル | 用途 | コスト比 |
|--------|------|---------|
| `opus` | 深い推論・設計判断・複雑なデバッグ | 50% |
| `sonnet` | 調査・実装・レビュー（広範読み取り中心） | 30% |
| `haiku` | テスト実行など結果確認のみ | 10% |

## 即時起動条件（ユーザー指示不要）

- コード変更直後 → `code-reviewer`
- セキュリティ関連コード → `security-reviewer`
- 新規ライブラリ・フレームワーク導入 → `spec-researcher`
- ドキュメント更新が必要 → `doc-updater`

## 並列実行

独立したタスクは並列でエージェントを起動する：

```markdown
# GOOD: 並列実行
1. Agent 1: auth.tsのセキュリティ分析
2. Agent 2: cacheシステムのパフォーマンスレビュー
3. Agent 3: utils.tsの型チェック

# BAD: 不要な逐次実行
agent 1 → agent 2 → agent 3 の順に実行
```

## 多角的分析

複雑な問題は役割分担したサブエージェントで検証する：
- 事実確認担当
- シニアエンジニア視点
- セキュリティ専門家視点
- 一貫性チェック担当
- 冗長性チェック担当

## 成果物レビュー原則

Agentツールにはeffort指定パラメータが無く、サブエージェント側のreasoning effortを外部から強制できない。委譲完了後の成果物レビューで品質を担保する：

- サブエージェントへの委譲完了後、成果物は必ず `effort: high` 以上に切り替えて親セッション自身がレビューする
- レビュー観点：要求範囲との一致・副作用の有無・`core-principles.md`（シンプル・根本原因・影響最小化）への適合
- レビュー完了後は元のeffort levelに戻す
