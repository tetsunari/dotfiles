# 浅いモジュールを深くする

浅いモジュールの集まりを1つの深いモジュールへ統合するとき、依存の種類ごとにテストの置き方を決める。
用語（モジュール・インターフェース・seam・アダプタ）は `../SKILL.md` の定義に従う。

出典: mattpocock/skills の `skills/engineering/codebase-design/DEEPENING.md`（2026-11-26 取得）を日本語に直して取り込んだ。MIT License, Copyright (c) 2026 Matt Pocock。

## 依存の4種類

統合の候補を見るとき、まず依存を分類する。分類で、統合後のモジュールを seam の向こうからどうテストするかが決まる。

### 1. プロセス内

純粋な計算、メモリ上の状態、I/O 無し。常に統合できる。モジュールをまとめ、新しいインターフェース越しに直接テストする。アダプタは要らない。

### 2. 手元で代替できる

テスト用の代替が手元で動く依存（Postgres に対する PGLite、メモリ上のファイルシステム）。代替があれば統合できる。テストは代替をテストスイートの中で動かして行う。seam はモジュール内部に置き、外向きのインターフェースに port は作らない。

### 3. ネットワーク越しだが自分たちのもの（Ports & Adapters）

ネットワークの向こうにある自分たちのサービス（マイクロサービス、社内 API）。seam に **port**（インターフェース）を定義する。ロジックは深いモジュールが持ち、通信手段は **アダプタ** として外から渡す。テストはメモリ上のアダプタ、本番は HTTP・gRPC・キューのアダプタを使う。

提案の形: 「seam に port を定義し、本番用に HTTP アダプタ、テスト用にメモリ上のアダプタを実装する。デプロイ先がネットワークで分かれていても、ロジックは1つの深いモジュールに収まる」

### 4. 本当に外部のもの（モック）

自分たちで制御できない外部サービス（Stripe、Twilio 等）。統合後のモジュールは外部依存を port として受け取り、テストはモックのアダプタを渡す。

## seam の規律

- port は、正当な理由のあるアダプタが2つ（通常は本番用とテスト用）揃うときだけ作る。アダプタが1つの seam は、間接参照が1段増えるだけ（`../SKILL.md` の原則「アダプタが1つなら仮の seam」）
- 深いモジュールは、外向きのインターフェースにある seam のほかに、内部の seam（実装の中だけで使い、自分のテストが使うもの）を持ってよい。テストが使うからといって、内部の seam をインターフェースに出さない

## テストは重ねずに置き換える

- 統合後のモジュールのインターフェースにテストができたら、浅いモジュールに付いていた古い単体テストは削除する
- 新しいテストは統合後のモジュールのインターフェースに書く。インターフェースがテスト面である
- テストはインターフェース越しに観測できる結果を検証する。内部の状態は見ない
- 実装を変えたときに直す必要のあるテストは、インターフェースより内側をテストしている
