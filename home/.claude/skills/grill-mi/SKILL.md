Use when user wants to stress-test a plan, get grilled on their design, or mentions "grill me" / "grill-mi" / "グリルして" / "問い詰めて" / "要件を固めたい" / "曖昧さを潰したい".

計画・設計のあらゆる側面について、共通理解に達するまで徹底的にインタビューする。決定を設計ツリーのノードとして扱い、「フロンティア」(前提条件が確定済みで質問可能な決定群)を軸に進める。

## 進め方

1. 現時点のフロンティア(前提が揃った質問)を洗い出し、番号付きで一度にまとめて提示する
2. 各質問には推奨する回答を添える。質問は「はい」と答えれば推奨回答を採用することになる文にする
3. ユーザーの回答を待つ
4. 回答をもとにフロンティアを再計算し、次ラウンドへ進む。同じラウンドで未回答の質問に依存する質問は、次以降のラウンドへ回す

質問フォーマット:
```
❓ **Q[番号]** - **<タイトル>**: <本文>
➡️ <推奨回答>
```

事実調査は自分の責務とし、ユーザーにファイルシステムやコードベースの確認を求めない。自身のRead/Grep/Globで足りない調査はAgentツールでサブエージェントに委託する。サブエージェントは今の会話を引き継がない新しいエージェントとして起動する（fork にしない）。調査を待つ間も、その結果に依存しない質問は今のラウンドで出す。待つのは調査結果に依存する質問だけにする。

決定はユーザーのものとする。調べて分かる事実と違い、自分で決めて進めない。

**ユーザーの前提が事実と食い違っていたら、質問より先にそれを提示する。** 前提がズレたまま質問を重ねても合意は積み上がらない。

## 用語の詰め方

インタビュー中に次のことをする。

- ユーザーが `CONTEXT.md` の定義と違う意味で語を使ったら、その場で指摘する（例:「CONTEXT.md では『キャンセル』を注文全体の取り消しと定義しているが、今の話は一部取り消しに聞こえる。どちらか」）
- 曖昧な語や複数の意味を持つ語には、正確な語を提案する（例:「『アカウント』は顧客と利用者のどちらか」）
- 概念どうしの関係を話しているときは、境界を突く具体的な場面を作って問う
- ユーザーの説明とコードの振る舞いが違えば指摘する
- 用語が決まったら、その場で `CONTEXT.md` に書く。最後にまとめて書かない。書き方は「完了後の成果物」の「CONTEXT.md の形式」に従う

設計判断の記録（ADR）は、次の3つが揃った決定だけ、`docs/adr/` への記録を提案する。1つでも欠けたら提案しない。

1. 後から変えると手間がかかる
2. 背景を知らない人が見ると、なぜそうしたか分からない
3. 実際に他の案があり、理由があって選んだ

`docs/adr/` が無ければ、最初の記録を書くときに作る。

## 終了判定

以下のいずれかで終了とする：
- ユーザーが「終わり」「OK」「十分」等で完了を示した
- フロンティアが空になった(設計ツリーの全ブランチを辿り、依存する決定が全て解決された)
- **最大20ラウンドを超えた場合は即座に終了。ユーザーに「十分な情報を収集しました」と明示。**（無限ループ防止）

## 完了出力

インタビュー終了時は以下を出力する：
```
## 合意した設計
[決定事項のサマリー]

## 未解決の懸念
[残課題があれば列挙。なければ「なし」]
```

## 完了後の成果物

インタビューの結果を、消えない形で残す。

### 1. 出力先の確認

**毎回 AskUserQuestion で確認する。** 自動判定しない。

- **Markdown** — リポジトリ内 `.scratch/` 配下
- **GitHub Issue** — `gh issue create`（未認証なら Markdown へ切り替え、その旨を伝える）

`.scratch/` に書く場合、**`.gitignore` に `.scratch/` が含まれているか確認**し、
無ければ追記の可否をユーザーに確認する。中間成果物を誤ってコミットする事故を防ぐ。

### 2. CONTEXT.md の形式

インタビュー中に確定したドメイン用語は、「用語の詰め方」のとおりその場でリポジトリ直下の `CONTEXT.md` に書いてある。
終了時は、確定した用語がすべて載っているかを確かめ、漏れがあれば足す。
`CONTEXT.md` が無ければ、最初の用語が決まったときに作る。

- **日本語で書く**（人間が読んで議論する資産のため）
- 形式は**日本語の概念名 ⇄ 英語の識別子**の対応表にする。
  コード上の識別子と会話の語彙が繋がり、`code-naming` の判断材料にもなる

```markdown
| 概念 | 識別子 | 意味 |
|---|---|---|
| 予約済み在庫 | `ReservedItem` | 注文確定前に確保された在庫。引当済みだが出荷前 |
```

既存の用語を勝手に書き換えない。追加と、明確な誤りの訂正のみ行う。

### 3. 理解の確認

**成果物を出して終わりにしない。** `close-the-gap` の理解度クイズに繋ぎ、
ユーザー自身の言葉で説明してもらう。

インタビューで合意したつもりでも、説明できなければ理解していない。
理解を外注しないことが、このステップの存在理由である。
