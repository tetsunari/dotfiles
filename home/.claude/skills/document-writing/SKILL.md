# ドキュメント作成ルール

## 目的

作業者が上からなぞるだけで、誰でも同品質の結果を出せるドキュメントを作る。
属人化を排除し、業務を標準化する。

## ノウハウ

### 読み手と目的
- 冒頭に、読者・目的・読み終えた人にどうなってほしいかを書く。読者に含めない人も書く
- 調べた経緯を時系列で並べない。読者に要る前提は「前提」の節に置き、書き手の調査メモは別のファイルに出す
- 元になった資料（Slack のスレッド・議事録・チケット）と日付、対象のバージョンを残す

### 表現
- 感情的な言葉・曖昧な表現を排除する
- 1文を短くシンプルにする
- 文字・画像の量は可能な限り最小限に抑える

### 構造
- インデントの階層は最大3つまで
- 各手順に項番を振り、進捗を把握しやすくする
- 入力項目が多い場合はテーブル（表）で整理する
- 文書内の別の箇所は、節番号や記号（§3 など）ではなく見出し名で指す。リンクを張れる媒体（Confluence、Markdown）では、その見出しへのページ内リンクにする
- 計画書・設計書の章は、上から読んで話がつながる順に並べる（例：背景 → 目的 → 何を作るか → いつ → 誰が → 守ること → 進め方 → リスク）。目的より先に背景を置く
- 見出しの直後に、別の見出しや表をいきなり置かない。前の節とのつながりと、その節に何があるかを1文で書く
- 定例ごとに更新する一覧（リスク表・課題一覧など）は子ページに分け、本体には要点と案内だけを残す。子ページと重複する細則は本体に書かない

### 見出し
- 中身を正確に指す、業界で普通に使う名詞にする（背景・目的・スコープ・スケジュール・体制など）。中身が絞れない管理用語、読み手に話しかける口調（「〜すること」「何を〜か」）、幼い言葉は避ける
  - 例：品質マネジメント → 出荷判定基準（中身が出荷の条件だけのとき）／やること → 作業計画／役割ごとにやること → 役割分担
- リンク先へ案内するだけの節には見出しを立てない。子ページ一覧の説明欄などにまとめる
- 新しい主語（ツール名・システム名など）は、前の節（目的など）で紹介してから使う。紹介なしで次の節の主語にしない
- 複数の話題を「・」で束ねた見出し（例：会議・リポジトリ・課題管理）にしない。上位の見出し（例：今後の進め方）でくくり、小見出しに分ける
- 見出し名を変える前・節を消す前に、その見出しを参照している箇所を grep で探して直す。消す内容は、別の場所（子ページなど）に書いてあることを確かめてから消す

### 再現性
- 書き手の環境にしかない前提（グローバル設定、権限モード、個人のパスやエイリアス）を手順や説明に書かない。配布する前に、手順が依存する設定がすべて文書の中で用意されるかを確かめる

### 効率
- コマンド・設定値はコピー＆ペーストで完結できるようにする

### 視覚
- リスクを伴う危険な作業箇所は **赤文字＋太文字** で強調する
- 画像に頼りすぎず、基本はテキストで伝える

### タイミング
- 作成を後回しにせず、実際の作業をしながらリアルタイムで作成する
- 長い文書は、本文を書く前に目次だけを出して依頼者と合意する。一度に全部書くと、直す箇所が文書全体に散らばる

## チェックリスト

ドキュメント出力前に自問する：

- [ ] 冒頭に読者・目的・読後の状態があるか
- [ ] 調べた経緯の時系列や書き手のメモが本文に混ざっていないか
- [ ] 元の資料・日付・対象バージョンが書いてあるか
- [ ] 長い文書なら、目次で合意してから本文を書いたか
- [ ] 1文が長すぎないか・曖昧語が混じっていないか
- [ ] インデントが3階層を超えていないか
- [ ] 各手順に項番が振られているか
- [ ] コマンド・設定値はそのままコピペで動くか
- [ ] 危険箇所が視覚的に強調されているか
- [ ] 不要な装飾・水増しがないか
- [ ] 別の箇所を節番号ではなく見出し名（リンク）で指しているか
- [ ] 書き手の環境だけにある設定、権限、パスに依存していないか
- [ ] 章が、上から読んで話がつながる順になっているか
- [ ] 見出しの直後に、つなぎの1文があるか
- [ ] 見出しが中身を正確に指す普通の名詞になっているか（話しかける口調・幼い言葉でないか）
- [ ] リンクで飛ばすだけの見出しが無いか
- [ ] 新しい主語（ツール名など）を、紹介する前に使っていないか
- [ ] 見出し名の変更・節の削除で、参照が切れていないか

## 仕上げ

チェックリスト通過後、`japanese-natural-writing` スキルの「他スキルからの仕上げ呼出し」に従い、手順・コマンド以外の説明文を自然化する。再適用する書式は本スキルの「構造」「視覚」。
